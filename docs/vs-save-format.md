## 0. TL;DR for the writer

1. Let the game create a **template world** headlessly (`VintagestoryServer --dataPath <dir>` with a prepared `serverconfig.json`), stop it.
2. Read `gamedata` -> `SaveGame.ModData["BlockIDs"]` to get the world's `code -> id` table. Use those ids. **[V]**
3. Delete the game-generated rows in `chunk` and `mapchunk` (keep `gamedata`, keep or drop `mapregion`).
4. For every converted chunk column `(cx, cz)` write **all** `MapSizeY/32` chunks (`chunk` table) + one `mapchunk` row.
5. Mapchunk: `currentpass = 6` (Done) and `WorldGenVersion = 3` => the game loads the column as-is, never regenerates it. **[V]**
6. Light: either compute it yourself (sunlight 22 above heightmap at least), or - only in a `superflat` world type - write
   `currentpass = 3` with empty light and let the game light the column (sun + block light) on first load. **[V]**
7. Write everything while the server is **not running**.

## 1. SQLite container

File: `<Saves>/<name>.vcdbs`, plain SQLite 3. Schema created by `SQLiteDbConnectionv2.CreateTablesIfNotExists` (Lib 116050-116105) **[V]**:

```sql
CREATE TABLE chunk     (position integer PRIMARY KEY, data BLOB);
CREATE TABLE mapchunk  (position integer PRIMARY KEY, data BLOB);
CREATE TABLE mapregion (position integer PRIMARY KEY, data BLOB);
CREATE TABLE gamedata  (savegameid integer PRIMARY KEY, data BLOB);   -- one row, savegameid = 1
CREATE TABLE playerdata(playerid integer PRIMARY KEY AUTOINCREMENT, playeruid TEXT, data BLOB);
CREATE INDEX index_playeruid on playerdata(playeruid);
```

- Writes are `INSERT OR REPLACE INTO chunk (position, data) VALUES (@position,@data)` (Lib ~115460). `position` is bound as `DbType.Int64` (20); the C# `ulong` is reinterpreted as signed `i64` => store `key as i64` in Rust. **[C]**
- Journal: with `CorruptionProtection` (default true) the game opens with `PRAGMA journal_mode=WAL; PRAGMA synchronous=Normal;` (API 150421). After a clean `/stop` the WAL is checkpointed (no `-wal` file left) **[V]**. Never write while the server holds the file.
- Version probe (`QuickCorrectSaveGameVersionTest`, Lib 116036): a v2 DB is recognised by the existence of table `gamedata`.

## 2. Position keys

`ChunkPos.ToChunkIndex` (Lib 116418-116440) **[V]**:

```
key(x, y, z, dim) = (u32)x | (u64)z << 27 | (u64)y << 54
                    | (dim & 0x1F) << 22          // only if dim != 0
                    | (dim & 0x3E0) << 44         // only if dim != 0
```

Decoding (`FromChunkIndex_saveGamev2`): `x = key & 0x3FFFFF` (22 bits), `z = (key>>27) & 0x3FFFFF`, `y = (key>>54) & 0x1FF`.
`y >= 1024` throws. **x and z are not masked on encode** (`(uint)x` is OR'ed raw) - they must be `0 <= x,z < 2^22`;
negative coordinates would corrupt the key. Dimension 0 = normal world.

| table | key | units |
|---|---|---|
| `chunk` | `key(chunkX, chunkY, chunkZ, dim)` | chunk coords = block / 32 |
| `mapchunk` | `key(chunkX, 0, chunkZ)` | chunk coords |
| `mapregion` | `key(regionX, 0, regionZ)` | region = 16 chunks = 512 blocks (`MagicNum.ChunkRegionSizeInChunks = 16`, Lib 43209) |

(GameDatabase.GetMapChunk/GetMapRegion: Lib 99757-99765.) Verified: test-world mapchunk `2146544139897` = `15993 | 15993<<27`;
mapregion `133949293542` = `998 | 998<<27`.

Note: the in-memory `MapChunkIndex2D` / `MapRegionIndex2D` (`(long)regionZ << 32 + regionX`, Lib 42623) are **different**
from the DB keys - only the DB keys above matter for us.

World coordinates: blocks are in `[0, MapSizeX) x [0, MapSizeY) x [0, MapSizeZ)`. The default spawn is the map center
`(MapSizeX/2, MapSizeZ/2)` (Lib 78787, 66234). Default MapSizeX/Z = 1 024 000 => center chunk 16000. Map MC `(0,0)` to the
VS map center (or to `DefaultSpawn`).

## 3. Protobuf conventions (applies to all blobs)

All blobs are **protobuf** (proto2-ish, protobuf-net). The game *reads* with `ProtoBuf.Serializer.Deserialize<T>` and
*writes* with a source-generated `FastSerialize` (`IWithFastSerialize`, API 46087) that emits standard protobuf wire format
(FastSerializer, API 45377+). So: **any correct protobuf encoder works**; field order is irrelevant for the reader **[V]**.

Details of what the game emits (useful for byte-identical output, not required):

- `int` fields: varint, **omitted when 0**; negative ints are written as 5-byte varints by FastSerializer (API ~45960), while
  protobuf-net writes 10-byte two's complement (seen in gamedata `RemainingUses=-1`). Both are accepted by the reader.
- `bool`: omitted when false, else varint 1.
- `byte[]`/`string`: LEN, omitted when null (an empty array is written as LEN 0).
- `ushort[]`/`int[]` (e.g. heightmaps): **repeated, unpacked** - one tag+varint per element, zeros included (tag byte `field*8`).
  protobuf-net also accepts packed.
- `Dictionary<string, byte[]>`: repeated LEN submessage `{1: key string, 2: value bytes}` (protobuf-net map convention).
- `Dictionary<int, string>`: repeated `{1: key varint, 2: value string}` (key 0 is still written by protobuf-net).
- `Vec4i`: LEN submessage `{1:X, 2:Y, 3:Z, 4:W}`; `BlockPos`: `{1:X, 2:InternalY, 3:Z}`.

(the game keeps a 1-entry palette `[0]` with header `-4`; our simpler `00000000` is also valid and what the game itself writes once the layer is null [V]).

### Chunk geometry

- Chunk = 32 x 32 x 32 blocks, 32768 cells (`ChunkData`, Lib 106268).
- **index3d = (y * 32 + z) * 32 + x**, with x,y,z local `0..31` (`MapUtil.Index3d(x,y,z,32,32)`, API 17200; used e.g. Lib 112946). **[V]**
- 2D index (heightmaps, snow): **index2d = z * 32 + x** (Lib 85925). **[V]**
- Column = `MapSizeY / 32` chunks, `cy = 0` is the bottom (`chunkMapSizeY = sizey / 32`, Lib 60233).

## 5. Layer codec (chunkdata version 2)

### 5.1 Compression: **Zstandard**

- `Compression.Compression1 = CompressionZSTD` (Lib 95486); every v2 call uses it (version != 0). Deflate is only used for version 0.
- Plain single zstd frames, no custom header. Game level: `-3` (`ZSTDCompressionLevel`, Lib 96001). Any level is fine.
- **Mandatory: the frame header must contain Frame_Content_Size.** The reader sizes its output buffer with
  `ZSTD_getFrameContentSize` (`ZStdWrapper.GetDecompressedSize`, Lib 96519) - a frame without content size returns
  `ZSTD_CONTENTSIZE_UNKNOWN` and decoding fails [C]. In Rust use `zstd::bulk::compress` / `zstd::bulk::Compressor`
  (one-shot `ZSTD_compress2`, content size included by default). Do **not** use `zstd::stream::Encoder` without
  `set_pledged_src_size`. Checksum flag: not needed (game frames have none) [V].
- All integers inside decompressed payloads are **little-endian int32**.

### 5.2 Block / fluid layer: "combined" format (fields 1 and 16)

Writer: `ChunkDataLayer.Compress` -> `Compression.CompressAndCombine` -> `ArrayConvert.Build` (Lib 95527, 95155-95210).
Reader: `Compression.DecompressCombined` (Lib 95598) **[V both directions]**.

```
int32 LE  h
if h == 0:          layer is null (all air / no fluid). Total blob = 4 zero bytes.
if h < 0:           palette stored raw: (-h) bytes = paletteCount * int32 LE      (game uses this when paletteCount <= 18)
if h > 0:           palette stored as a zstd frame of h bytes (decompresses to paletteCount * int32 LE)   (paletteCount > 18)
then:               zstd frame (rest of the blob) = bit-planes: nbits * 1024 int32 LE
```

- `paletteCount <= 1` on read => layer null (treated as all zero).
- **nbits on read = log2(roundUpPow2(paletteCount))** (`GetRoundedUpSize`, Lib 95473). On write the game emits `log2(palette.Length)`
  planes where its palette array length is a power of two >= paletteCount. Writer rule: `nbits = ceil(log2(paletteCount))`
  (min 1), emit exactly `nbits` planes. The reader throws `InvalidDataException` if fewer than `nbits*4096` bytes decompress.
- `nbits <= 15` (`dataBits = new int[15][]`), i.e. at most 32768 palette entries.
- **palette[0] must be 0** (air for blocks, "no fluid" for fluids). The game always reserves index 0 for value 0
  (`NewDataBitsWithFirstValue`, `PopulateWithAir`, Lib cdl 517-742); edit code (`SetZero`, `Set`) relies on it.
- Bit-planar packing (`GetFromBits*`, `GetUnsafe`): plane `k` is `int32[1024]`; cell `i` uses word `i >> 5`, bit `i & 31`:

```
paletteIndex(i) = sum_k ((plane[k][i >> 5] >> (i & 31)) & 1) << k
value(i)        = palette[paletteIndex(i)]
```

Rust sketch:

```rust
fn encode_block_layer(cells: &[u32; 32768]) -> Vec<u8> {
    if cells.iter().all(|&v| v == 0) { return vec![0; 4]; }
    let (palette, idx) = build_palette_with_zero_first(cells);   // palette[0] == 0
    let nbits = (usize::BITS - (palette.len() - 1).leading_zeros()).max(1) as usize; // ceil(log2)
    let mut planes = vec![0u32; nbits * 1024];
    for (i, &p) in idx.iter().enumerate() {
        for k in 0..nbits { if (p >> k) & 1 == 1 { planes[k * 1024 + (i >> 5)] |= 1 << (i & 31); } }
    }
    let data = zstd::bulk::compress(bytemuck::cast_slice(&planes_le), 3)?;
    let pal_bytes: Vec<u8> = palette.iter().flat_map(|v| (*v as i32).to_le_bytes()).collect();
    let mut out = Vec::new();
    if palette.len() > 18 {
        let pz = zstd::bulk::compress(&pal_bytes, 3)?;
        out.extend((pz.len() as i32).to_le_bytes()); out.extend(pz);
    } else {
        out.extend((-(pal_bytes.len() as i32)).to_le_bytes()); out.extend(pal_bytes);
    }
    out.extend(data);
    out
}
```

(Both palette encodings are accepted for any count; the 18 threshold just mirrors the game. Both paths verified: 26-entry
palette with `h>0` and 4-entry raw palette with `h<0` round-tripped through the server.)

### 5.3 Light layer (fields 2 + 3)

Writer: `ChunkDataLayer.CompressSeparate` (cdl 772); reader: `DecompressSeparate` (cdl 825). **[V]**

- Field 2 `lightCompressed` = zstd frame of `nbits * 1024` int32 LE bit-planes (same packing as 5.2).
- Field 3 `lightSatCompressed` = zstd frame of `paletteCount` int32 LE palette entries (not padded).
- `nbits` must equal `log2(roundUpPow2(paletteCount))` (else "Corrupted light data?" + padding with empty planes).
- Either field empty (LEN 0) => `lightLayer = null` => all light reads return 0.
- Decompressed plane size must be a multiple of 4096 bytes.

Light value (uint, per cell; ChunkData Lib 106820-106960, ChunkIlluminator Lib ~105070):

```
bits 0-4   sunlight level      (0..31; server sunBrightness, = 22 with the survival mod: SurvivalConfig.SunBrightness, Surv 132866)
bits 5-9   block light level   (value of the light HSV)
bits 10-15 block light hue
bits 16-18 block light saturation
```

Observed after the game lit a column with a torch [V]: open sky = `22`; next to a torch `266710` = sun 22, block 14, hue 4, sat 4.
Air chunks above terrain = palette `[0, 22]`, 1 plane, all ones.

### 5.4 What the game writes for a superflat bottom chunk [V]

`blocks: h=-16, palette [0, 4604 rock-claystone, 6670 soil-medium-none, 6685 soil-medium-normal], 2 planes`;
`light: palette [0, 22]`; `liquids: 00000000`; `f12 "1.22.7"`; `f15 = 2`.

### 5.5 Fluids

- VS 1.22 has two block layers per cell: solid (field 1) and fluid (field 16). The combined view returns the solid block if != 0
  else the fluid (`ChunkData.this[]`, Lib 106330).
- Water/lava/etc. (blocks whose class has `ForFluidsLayer == true`, API 121028; BlockForFluidsLayer subclasses) **must go to
  field 16**. Waterlogged = solid block in field 1 + water in field 16 at the same index.
- Option [C/U]: writing `savedCompressionVersion = 1` makes the game run `ChunkData.UpdateFluids()` on unpack (Lib 45703,
  105668), which moves every `ForFluidsLayer` palette entry out of the solid layer and applies `RemapToLiquidsLayer`.
  Not tested; prefer splitting layers ourselves.

### 6.1 Generation state - how to stop the game from (re)generating

`EnumWorldGenPass` (API 8286): `None=0, Terrain=1, TerrainFeatures=2, Vegetation=3, NeighbourSunLightFlood=4, PreDone=5, Done=6`.
`currentpass` is the **next incomplete** pass; `PopulateChunk` runs the handlers of `currentpass` and increments it (Lib 79127-79155).

Load logic `loadOrGenerateChunkColumn_OnChunkThread` (Lib 77994-78063) + `TryLoadChunkColumn` (Lib 78648):

1. Mapchunk is loaded from DB. `flag = currentpass >= Done || WorldGenVersion >= 3`.
2. If `!flag && WorldGenVersion != 0` => mapchunk **re-created** and column regenerated from scratch.
3. If `flag`: read all `ChunkMapSizeY` chunks of the column. **If only some exist: "Loaded some but not all chunks of a column?
   Discarding whole column." => regenerated.** If none exist => `GenerateNewChunkColumn` (terrain from seed).
4. If `currentpass == Done` => column is loaded as-is. Otherwise the remaining passes run on our data
   (needs the 8 neighbours at >= the same pass; missing neighbours get generated).

=> **Write `currentpass = 6`, `WorldGenVersion = 3`, and every chunk of the column.** [V: 49 injected Done columns at spawn
loaded unchanged, no regeneration, no new columns, nothing re-saved].

Pass handlers registered by the stock mods (matters if you choose `currentpass < 6`):

| pass | `standard` world type | `superflat` world type |
|---|---|---|
| Terrain (1) | GenTerra, GenBlockLayers, caves, rivers, ... (Ess) | GenBlockLayersFlat (Crea 427) - overwrites everything |
| TerrainFeatures (2) | deposits, structures, ponds, hot springs, ... | nothing |
| Vegetation (3) | GenVegetationAndPatches (trees!), GenRivulets, GenStoryStructures, GenLightSurvival (0.95: `SunFloodChunkColumnForWorldGen` + `RunScheduledBlockLightUpdates`) | **only GenLightCreative** (same light code, Crea 520) |
| NeighbourSunLightFlood (4) | GenSnowLayer (adds snow by climate), GenLightSurvival neighbour flood | GenLightCreative neighbour flood |
| PreDone (5) | GenCreatures (spawns animals) | nothing |

### 6.2 Neighbour/border effects [C/U]

When a player walks off the converted area the game generates new columns there; their TerrainFeatures/Vegetation passes
may write into adjacent (our) chunks (trees, structures spilling over). Terrain will not match at the seam
(`requiresChunkBorderSmoothing` only applies to worlds with `CreatedWorldGenVersion != 3`, Lib 77695). Options: convert a
margin, set a small MapSizeX/Z, or accept it.

## 7. `mapregion` blob = `ServerMapRegion` (Lib 46744)

Climate/forest/geologic/ore maps, generated structures. **Do not write it.** If a region row is missing the game builds it from
the seed via `OnMapRegionGen` (`GetOrCreateMapRegion...` Lib 78480-78540) without touching chunks [C]. Keep the template's rows
or delete them; deleting is safe [U - not exercised, the tests kept them].

### 8.1 Block id <-> code mapping

- Stored in `SaveGame.ModData["BlockIDs"]` (`LoadStoredBlockCodesById` / `StoreBlockCodesById`, Lib 72460-72525).
- Value = protobuf-net `Dictionary<int,string>`: repeated field 1 `{1: id varint, 2: code string}`. Codes are
  `AssetLocation.ToShortString()` => the `game:` domain is **omitted** (`"rock-granite"`), other domains kept (`"mymod:foo"`).
  Test world: 14091 entries, ids 0..14090, `0 = "air"`, `1 = "mantle"` [V]. Items likewise in `ItemIDs`.
- On every start the server loads the stored map and **remaps its runtime blocks to the stored ids** (Lib 72200-72445):
  stored ids are authoritative; blocks no longer present become "unknown" placeholders; new blocks get fresh ids (> max).
  So ids are stable per world, and **the ids of a game-created template world are exactly what our chunks must use** [V:
  injected ids 4605/342/9665/7416/4599-4622 survived load + re-save unchanged].
- Building a world with no `BlockIDs` (flag `val5.Count == 0`) lets the game assign ids in registration order - do not rely on it.
  Writing our own complete BlockIDs table should work by the remap logic [U] but needs the full list of block codes; using a
  template is simpler.
- Same mod set + game version must be used when the world is opened later, else ids get remapped (fine) or blocks go missing.

## 9. Lighting

- On load, a `Done` column with empty light (fields 2/3 LEN 0) is **not relit** by the server: it stayed empty and was never
  re-saved [V]. Light 0 everywhere => the column would render dark [U - client not tested].
- There is no relight flag in the save. Runtime relight exists only as a debug command `/debug chunk relight [pos]`
  (`FullRelight` over one chunk, Lib 61411, 62183) - impractical for whole worlds.
- **Game-computed lighting (superflat world type only)** [V]: write `currentpass = 3` (Vegetation), empty light, correct `YMax`,
  and optional `ScheduledBlockLightUpdates` entries (field 17) for every light-emitting block. On first load the server runs
  GenLightCreative (sun fill + vertical trace + flood, then block light from field 17), then the neighbour flood, then PreDone,
  and saves the column with `currentpass = 6`. Neighbours must be at >= pass 3 (or they get generated as superflat terrain).
  Lazy: happens only when the column gets loaded (player proximity / spawn area).
- With `WorldType = standard`, `currentpass = 3` would also grow trees, rivulets and story structures on our terrain - do not.
  `currentpass = 4` in standard runs snow layer + neighbour sun flood, `5` runs creature spawning only [C]; both still need our own
  base sunlight because the per-column sun fill is in pass 3.
- **Self-computed minimum** (works with any world type): for each (x,z) set sunlight = sunBrightness (22) for every cell above
  `RainHeightMap[x,z]`, 0 below; light palette `[0, 22]`. Verified to load [V]; quality is lower (no horizontal flood under
  overhangs, no torch light until a block update). A fuller port of `ChunkIlluminator.Sunlight/SunlightFlood` (Lib 104299+,
  uses per-block `LightAbsorption`, decrement per block) is possible later.

## 10. Recommended strategy (validated)

1. Prepare a dataPath (never `~/.config/VintagestoryData`), run `VintagestoryServer --dataPath D --genconfig`, then edit
   `D/serverconfig.json`: `WorldConfig.SaveFileLocation`, `WorldName`, `WorldType` ("superflat" or "standard"),
   `PlayStyle`/`PlayStyleLangCode`, `Seed`, `MapSizeY` (top-level, e.g. 384 for MC 1.18+: -64..319 -> 0..383), maybe
   `MapSizeX/Z`, `Port`.
2. `(sleep 60; echo /stop) | DOTNET_ROOT=$HOME/.dotnet ./VintagestoryServer --dataPath D` -> template `.vcdbs` with 7x7
   Done spawn columns + 15x15 partial ones (~30 s on this machine).
3. Read BlockIDs. Build the MC-blockstate -> VS-code table, resolve codes to ids.
4. `DELETE FROM chunk; DELETE FROM mapchunk;` then insert our columns (all `MapSizeY/32` chunks each) and mapchunks
   (`currentpass` 6 or 3 as per section 9, `WorldGenVersion` 3, heightmaps, `YMax`). Optionally set `DefaultSpawn`.
5. Start the server once to check logs (`Logs/server-main.log`, look for "Failed deserializing").

Validation runs (all under the scratchpad, see top):
- run 2: replaced 2 spawn columns; the `currentpass=3` column came back lit (sun + torch light), pass 6, blocks identical bit-for-bit
  after the game's own re-encode; the `currentpass=6` column was left untouched.
- run 4: deleted every chunk/mapchunk, injected a 7x7 spawn area: no regeneration, no extra columns, only the pass-3 column
  re-saved (lit); the Done + no-light column stayed without light.

## 11. Open questions / risks

- Block entities (chests, signs, torches' transient BE, flower pots...) are not written: blocks whose class expects a BE
  (e.g. `torch-*`, chests) will exist without it. Need per-type TreeAttribute writers (field 8) - not specified here.
- Client-side appearance of unlit Done chunks not checked in a real client.
- `TopRockIdMap`, `SedimentaryThicknessMap`, `CaveHeightDistort` absence effects not exercised (only worldgen should use the last two).
- Brand-new columns far from spawn were not observed being loaded (no player connected); the load path is the same code as the
  spawn columns, so expected to behave identically [C].
- Deleting `mapregion` rows untested; snow/climate in a standard world come from regenerated regions => climate will not match
  the MC biomes.
- MapSizeY other than 256 not tested (should be any multiple of 32).
- Sun brightness: 22 assumed (survival mod config). If a world config changes it, light written by us must match
  `server.sunBrightness`.
